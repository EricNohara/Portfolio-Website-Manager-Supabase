# Executive Summary

Current status:

**Overall readiness:** 6.5/10

The application architecture is good and the project is much farther along than most independent developer SaaS products at this stage.

However, I found several issues that I would classify as **launch blockers**, particularly around security.

The good news:

- most of these are architectural mistakes rather than code quality problems
- they appear fixable without major rewrites
- I did not yet find evidence of catastrophic credential leaks

The biggest concern is that there are multiple places where an attacker could potentially:

- access data they should not
- abuse paid AI endpoints
- cause excessive cloud costs
- delete user assets

# 1. Anonymous access to privileged database functionality

Severity:
🔥 Critical

From the current implementation it appears anonymous callers can invoke privileged database functionality that should only execute for authenticated users.

Potential impact:

- read another user's information
- modify records
- enumerate data
- bypass application authorization

Recommendation

Every database RPC/function should validate:

```
auth.uid()
```

inside the function.

Do not trust:

- client IDs
- profile IDs
- API parameters

Always derive identity from Supabase auth.

---

# 2. Cross-tenant access via "Super Key"

Severity:
🔥 Critical

Current implementation suggests user-controlled "Super Keys" can be used to retrieve information across tenants.

That creates an authorization boundary issue.

Potential attacks:

- guessable keys
- leaked key descriptions
- privilege confusion
- accidental exposure

Recommendation

Super Keys should:

- never be user generated
- be cryptographically random
- have server-side ownership validation
- expire when appropriate
- never directly identify another tenant

---

# 3. Service Role Storage Deletes

Severity:
🔥 Critical

Storage deletion appears to use Service Role credentials.

If ownership checks are missing before deletion:

User A could delete User B assets.

Recommendation

Every delete must verify:

```
current user owns object
```

before service role deletion occurs.

Never trust filenames.

Never trust bucket paths.

Verify owner in database first.

---

# 4. AI Cost Abuse

Severity:
🔥 Critical

This is probably the largest financial risk.

Current AI endpoints appear callable without strong cost controls.

An attacker could:

- spam resume generation
- spam headshots
- spam cover letters
- repeatedly regenerate outputs

This can rapidly become expensive.

Recommendation

Every AI endpoint needs:

✓ authentication

✓ rate limiting

✓ per-user quotas

✓ credit validation

✓ atomic credit deduction

✓ rollback on failure

---

# 5. Credit Race Conditions

Severity:
🔥 Critical

Current flow appears vulnerable to concurrent requests.

Example:

User has:

1 credit

Opens:

10 browser tabs

Clicks Generate.

If deduction occurs after generation:

10 AI calls execute.

Recommendation

Credits should be deducted:

inside a transaction

before generation begins.

If generation fails:

refund credit.

---

# 6. Missing Abuse Controls

Severity:
🔥 Critical

Public APIs appear to lack:

- IP throttling
- request throttling
- burst protection

Without this:

Someone can continuously call endpoints.

Recommendation

Use:

- Upstash Rate Limit
- Vercel Edge Middleware
- Redis counters

Protect:

- login
- signup
- AI generation
- API key creation
- password reset

# 7. Object Ownership Validation

Never trust:

```
userId
```

sent from browser.

Every update should verify

```
resource.owner == auth.uid()
```

---

# 8. API Key Controls

Need:

- expiration
- rotation
- last used
- scopes
- revoke

Never expose full key after creation.

Store hash only.

---

# 9. File Upload Validation

Need:

- MIME validation
- size limits
- extension validation
- image verification

Otherwise attackers can upload arbitrary files.

---

# 10. Storage Quotas

Need limits for:

- number of uploads
- total storage
- image size

Otherwise storage bills become attack vectors.

---

# 11. Signed URLs

Ensure storage objects are:

private

Only issue signed URLs.

Never expose public bucket paths.
