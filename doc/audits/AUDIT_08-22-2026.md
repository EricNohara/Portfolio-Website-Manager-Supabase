**Repository:** EricNohara/Nukleio  
**Audit type:** Full static application and database review  
**Audit date:** August 22, 2026  
**Compared with:** `doc/audits/AUDIT_07-24-2026.md`  
**Audit status:** Complete for repository-visible code and configuration

> This is a strict, evidence-based static audit. It covers the application code,
> API routes, migrations, RLS policies, RPC privileges, storage flows, AI credit
> accounting, billing, authentication, account deletion, configuration, and
> repository quality gates. It does not claim to verify settings or policies
> that exist only in hosted Supabase, Stripe, Vercel, or AI-agent deployments.

---

# Executive Summary

**Overall readiness:** 6.2/10  
**Public launch recommendation:** **Do not launch publicly yet**

Nukleio is materially safer than it was on July 24. The most dangerous
cross-tenant database defects identified in the first audit have been corrected
in the repository:

- anonymous table and routine privileges are revoked
- the description-based Super Key behavior is removed
- privileged RPCs are explicitly restricted
- service-role storage deletes validate ownership and expected namespaces
- AI credits are deducted atomically before generation
- duplicate credit operations are idempotent
- failed generation attempts normally refund consumed credits
- cached premium AI data is no longer directly available through the
  authenticated Data API
- account deletion now uses a deletion lock and performs storage cleanup

Those are meaningful improvements. The application no longer appears to have
the obvious cross-tenant read/write path that made the first audit a 5/10.

However, the financial-abuse boundary is still not ready for an unrestricted
public launch. A user receives free AI credits immediately after signup, while
email confirmation and CAPTCHA are disabled and application-level throttling is
absent. Storage uploads also have no per-user quotas or request-rate controls.
This makes account farming and storage-cost abuse practical.

The second major concern is the AI-agent trust boundary. Every application call
to an agent sends only JSON and no service credential, signature, or bearer
token. At least one Lambda Function URL is published in the CSP. If the agent
deployments do not independently require strong authentication, an attacker can
call them directly, bypassing Nukleio authentication, tiers, credits, and
logging. That must be verified and fixed before launch.

The report contains three P0 launch blockers, ten P1 findings, and a set of P2
hardening and assurance gaps.

# Priority Findings

## P0 — Must Fix Before Public Launch

## 1. AI-agent endpoints have no application-to-agent authentication

**Severity:** Critical  
**Status:** Open; deployment verification required

The resume, cover-letter, and headshot routes call their respective agent URLs
with only `Content-Type: application/json`. They do not send a bearer token,
HMAC signature, mTLS identity, AWS SigV4 request, timestamp, or replay nonce.

Evidence:

- `app/api/internal/user/aiAgents/resume/route.ts:445-449`
- `app/api/internal/user/aiAgents/coverLetter/route.ts:319-323`
- `app/api/internal/user/aiAgents/coverLetter/route.ts:537-541`
- `app/api/internal/user/aiAgents/headshot/route.ts:334-338`
- `app/api/internal/user/aiAgents/headshot/route.ts:473-477`
- `next.config.ts:81-93` publishes a Lambda Function URL in `connect-src`

If the deployed agent endpoints are publicly callable, an attacker can bypass:

- Nukleio authentication
- subscription-tier enforcement
- AI credit consumption
- idempotency checks
- application logging
- account-deletion locks

This would make the new credit system irrelevant as a cost control.

Required remediation:

1. Require authentication at every agent deployment.
2. Prefer a private network or authenticated gateway. At minimum, sign each
   request with a server-only HMAC containing method, path, body digest,
   timestamp, nonce, user ID, and operation.
3. Reject stale timestamps and reused nonces at the agent.
4. Never put the credential in a `NEXT_PUBLIC_*` variable or browser request.
5. Apply agent-side per-user and global rate limits even after authentication.
6. Remove obsolete agent URLs from CSP and public configuration.
7. Test that a direct unsigned request is rejected before it reaches a paid
   model or image-generation provider.

Do not accept “the URL is secret” as authentication. The repository already
contains one concrete Lambda URL, and URLs leak through logs, errors, browser
headers, and infrastructure metadata.

## 2. Free-credit signup can be farmed to create unbounded AI cost

**Severity:** Critical  
**Status:** Open

Every new Auth user receives three lifetime AI credits in
`20260810180000_add_ai_credits.sql`. A cover letter costs three credits and
other operations can also consume the grant.

At the same time, repository configuration shows:

- email confirmation disabled: `supabase/config.toml:219-226`
- CAPTCHA disabled/commented: `supabase/config.toml:213-217`
- signup enabled: `supabase/config.toml:175-176`
- signup/sign-in limited only to 30 requests per five minutes per IP in local
  configuration: `supabase/config.toml:197-211`
- no application-level IP, account, device, or global AI-generation limiter
- no equivalent deployment configuration committed for verification

Credits correctly limit one account, but they do not limit the number of
accounts. Proxies, botnets, IPv6 ranges, and disposable email addresses make an
IP-only Auth limit insufficient. Thirty fresh accounts from one IP can obtain
ninety free credits per five-minute window under the committed local settings.

Required remediation:

1. Enable email confirmation in the hosted Auth project.
2. Enable Turnstile or hCaptcha for signup and password recovery.
3. Do not grant usable AI credits until email verification and abuse checks
   complete.
4. Add distributed limits for signup and AI routes by IP, user, operation, and
   global spend window.
5. Add burst limits and a hard global daily cost ceiling.
6. Alert on signup velocity, failed CAPTCHA, repeated device fingerprints,
   credit consumption velocity, and abnormal agent/provider spend.
7. Consider requiring a verified payment method before high-cost image work.

The atomic ledger fixes concurrent overspending, but it does not solve identity
farming. Public launch remains financially unsafe until both layers exist.

## 3. Authenticated storage consumption is effectively unbounded

**Severity:** Critical  
**Status:** Open

`POST /api/internal/storage` allows any authenticated account to upload files
to four service-role-managed buckets. Each request may contain up to 50 MiB, but
there is no per-user object count, total-byte quota, upload-rate limit, tier
limit, or global storage budget.

Evidence:

- allowed buckets: `app/api/internal/storage/route.ts:19-24`
- request parsing: `app/api/internal/storage/route.ts:50-60`
- 50 MiB per-request limit: `app/api/internal/storage/route.ts:82-89`
- service-role upload: `app/api/internal/storage/route.ts:92-98`
- project-thumbnail uploads return before requiring a project association:
  `app/api/internal/storage/route.ts:178-182`
- no rate-limit implementation exists in the repository

The headshot route is worse: it accepts one or two multipart image files with no
explicit size limit before service-role upload (`headshot/route.ts:182-218`).

An attacker can create many accounts, upload repeated 50 MiB files, and leave
orphaned project thumbnails. This can exhaust storage, memory, serverless body
limits, bandwidth, and operational budgets without consuming AI credits.

Required remediation:

1. Enforce small route-specific byte limits before buffering content.
2. Track object count and total stored bytes per user transactionally.
3. Reject uploads when quota is exhausted.
4. Add per-user/IP upload-rate and concurrent-upload limits.
5. Associate project uploads with a pending project/upload record and delete
   abandoned objects automatically.
6. Add bucket lifecycle cleanup for unreferenced temporary inputs.
7. Add a global storage/bandwidth budget alarm and emergency deny switch.

# P1 — High Priority

## 4. Sensitive user documents appear to use public object URLs

**Severity:** High  
**Status:** Open / hosted bucket state not verified

Resumes, transcripts, portraits, project images, AI resumes, and headshot inputs
are represented with `getPublicUrl()` values. The UI consumes those values
directly, and AI agents receive them as fetchable URLs.

Evidence:

- `app/api/internal/storage/route.ts:110-121`
- `app/api/internal/user/aiAgents/headshot/route.ts:274-310`
- the parser accepts only `/storage/v1/object/public/` URLs:
  `utils/general/parseURL.ts:13-33`

Resumes and transcripts commonly contain addresses, phone numbers, education
records, employment history, signatures, and other personal information.
Unguesseable object names reduce enumeration risk but do not provide revocation,
authorization, or confidentiality when URLs leak through logs, referrers,
browser history, screenshots, third-party agents, or support systems.

Required remediation:

- make all customer buckets private
- store bucket and object path, not permanent public URLs
- issue short-lived signed URLs only after authorization
- use narrowly scoped signed upload URLs where practical
- separate genuinely public portfolio assets from private documents
- verify deployed bucket listing and read policies explicitly

## 5. File validation trusts attacker-controlled MIME metadata

**Severity:** High  
**Status:** Open

The general storage route checks `file.type`, and image uploads accept any
`image/*`. It does not inspect magic bytes, decode images server-side, reject
SVG, validate PDFs structurally, or normalize content before publishing it.

Evidence:

- `app/api/internal/storage/route.ts:64-80`
- `app/api/internal/user/aiAgents/headshot/route.ts:190-218`
- client compression falls back to the original unverified file on errors:
  `utils/file-upload/compress.ts`

Consequences include public malware hosting, polyglot files, decompression
bombs, parser attacks against downstream agents, and script-capable SVG content
served from a trusted Supabase hostname.

Required remediation:

- allowlist exact formats: JPEG, PNG, WebP, and PDF as needed
- reject SVG and ambiguous formats unless sanitized by a proven pipeline
- verify magic bytes and decode/re-encode images server-side
- load PDFs with strict limits and reject encrypted, malformed, oversized-page,
  or excessively complex documents
- set `X-Content-Type-Options: nosniff` on delivery where controllable
- scan documents for malware before making them available

## 6. Public API has no rate limits, quotas, or bounded logging

**Severity:** High  
**Status:** Open

`GET /api/public/getUserData` is intentionally cross-origin and authenticates a
strong API key correctly, but it has no per-key, per-IP, tenant, or global
limits. Every valid request schedules a database log write and updates
`last_used`.

Evidence:

- public route and wildcard CORS: `app/api/public/getUserData/route.ts:6-18`
- service-role RPC lookup: `app/api/public/getUserData/route.ts:25-55`
- per-request log mutation: `app/api/public/getUserData/route.ts:71-92`
- API-key descriptions and user-agent strings are not length-bounded in the
  schema or route

A leaked or intentionally shared key can generate unbounded reads, log writes,
bandwidth, and database growth. Key owners also have no scopes or explicit
request quotas.

Required remediation:

- distributed per-key and per-IP rate limiting
- per-plan monthly API quotas and short burst limits
- bounded user-agent and description lengths
- log sampling or aggregation for high-volume clients
- key scopes and explicit usage policies
- global abuse/cost circuit breaker

## 7. AI input size, output size, and upstream duration are not bounded

**Severity:** High  
**Status:** Open

Cover-letter job descriptions, writing samples, revision feedback, target-job
arrays, selection arrays, headshot feedback, and PDF drafts have no meaningful
length or item-count limits. The application also calls agents without an
`AbortSignal` timeout and reads unbounded JSON responses.

Evidence:

- cover-letter input: `coverLetter/route.ts:258-310`
- cover-letter revision feedback: `coverLetter/route.ts:456-528`
- resume arrays accept arbitrary counts and string lengths:
  `resume/route.ts:116-193`
- PDF generation accepts arbitrary text: `coverLetter/pdf/route.ts:16-29`
- all five agent `fetch` calls omit a timeout

Risks:

- memory and CPU exhaustion
- excessive provider tokens and unexpectedly high cost per credited request
- serverless duration exhaustion
- credits remaining consumed if the platform kills the invocation before the
  `catch` block can refund them
- huge agent responses being persisted as JSON or text

Required remediation:

- schema-validate every AI request with maximum lengths and array counts
- cap total serialized payload size and estimated token count
- add strict upstream connect and total timeouts with `AbortController`
- cap response bytes before parsing
- move long-running generation to an idempotent job queue
- reconcile stuck charges asynchronously rather than relying only on `catch`
- apply provider-level maximum output tokens and image limits

## 8. Headshot revision creates a downstream SSRF and cross-user input boundary

**Severity:** High  
**Status:** Open

The revision route accepts an arbitrary client-provided `headshotUrl` and sends
it to the headshot agent. It does not require the URL to belong to the current
user, to use the configured Supabase origin, or to exist in that user's cached
headshot rows.

Evidence:

- request type: `app/api/internal/user/aiAgents/headshot/route.ts:47-56`
- validation checks only that it is a string: `headshot/route.ts:90-105`
- forwarded to the agent: `headshot/route.ts:468-477`

If the downstream agent fetches the supplied URL, attackers can make it request
localhost, cloud metadata, internal services, oversized resources, or other
users' public images. Nukleio cannot delegate this validation exclusively to an
agent it calls as a privileged service.

Required remediation:

- accept a server-issued headshot ID, not an arbitrary URL
- look up the row by both ID and authenticated user ID
- derive the storage path server-side
- require the path to be in `generated/{userId}/...`
- independently block private, loopback, link-local, metadata, and non-HTTPS
  destinations at the agent fetch layer

## 9. Billing checkout accepts any syntactically valid Stripe price ID

**Severity:** High  
**Status:** Open

The checkout route checks only that `priceId` starts with `price_`. It does not
require the value to match one of the four configured Nukleio plans.

Evidence: `app/api/internal/stripe/checkout/route.ts:22-25`

An authenticated user who learns another active price ID in the same Stripe
account can create an unintended checkout session. Unknown prices currently map
to the free tier locally, which limits direct privilege escalation, but the
behavior can still expose retired, internal, test, discounted, or otherwise
unsupported products and can strand the user in an active subscription that
blocks normal checkout.

Required remediation:

- resolve the requested price through the same server-side allowlist used by
  tier calculation
- reject every unknown price ID
- retrieve the Stripe Price and verify active status, currency, recurring
  interval, product ID, and expected amount
- add idempotency keys and a transaction/lock to prevent concurrent checkout
  requests from creating multiple customers or subscriptions

## 10. Destructive account actions do not require recent reauthentication

**Severity:** High  
**Status:** Open

Account deletion requires a phrase, email, acknowledgement, and same-origin
request, which is better than the first audit. It does not require the current
password, an MFA challenge, or a recently authenticated session.

Evidence:

- deletion confirmation: `app/api/internal/user/route.ts:95-149`
- password changes do not require recent authentication in committed config:
  `supabase/config.toml:227-228`
- the password reset/update page changes a password using any signed-in client
  session: `app/passwordReset/page.tsx`

A stolen but still-valid session can permanently delete the account and its
Stripe customer or change the password. The confirmation email is readable from
the session-backed profile and is not a second factor.

Required remediation:

- require recent reauthentication for account deletion, password changes, API
  key rotation, and billing-sensitive actions
- enable Supabase secure password change
- require MFA when enrolled
- notify the user out of band before and after destructive security changes
- consider a recoverable deletion grace period rather than immediate hard delete

## 11. Unsafe authenticated default database privileges remain

**Severity:** High  
**Status:** Open as a regression hazard

The initial schema grants default CRUD privileges on future public tables and
default execution on future routines to `authenticated`:

- `20260724161653_initial_production_schema.sql:13-17`

The later anonymous-lockdown migration revokes unsafe defaults for `anon` and
`PUBLIC`, but it does not revoke the authenticated defaults. Newer migrations
carefully revoke privileges on sensitive objects, so no current high-impact
function was found exposed accidentally. The default nevertheless makes every
future table and routine reachable until its author remembers to revoke it.

This is especially dangerous for future `SECURITY DEFINER` functions because
PostgreSQL also commonly grants routine execution broadly by default.

Required remediation:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  REVOKE ALL PRIVILEGES ON TABLES FROM authenticated;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  REVOKE ALL PRIVILEGES ON SEQUENCES FROM authenticated;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
  REVOKE ALL PRIVILEGES ON ROUTINES FROM authenticated;
```

Grant only the exact privileges each migration needs. Add a database test that
fails when `anon`, `PUBLIC`, or `authenticated` has an unexpected privilege.

## 12. Authenticated users can bypass application validation through Data API

**Severity:** High  
**Status:** Open by architecture

RLS now prevents cross-tenant access, but several tables intentionally allow an
authenticated user to manage all of their own rows directly. This means the
Next.js route validation is not a security boundary. A user can bypass field
length checks, API-key count limits, cache-refresh logic, and route-level
business rules by calling Supabase directly with the browser publishable key.

Examples:

- `api_keys` owner policy allows all commands
- profile, skill, experience, education, course, and project owner policies
  allow direct mutations
- most text and array columns have no database length/count checks

Cross-tenant RLS appears correct, so this is not the former critical exposure.
It is still a data-integrity and resource-abuse issue.

Required remediation:

- put invariant checks in database constraints or service-role-only RPCs
- cap text lengths and array sizes in SQL
- cap per-user row counts where appropriate
- expose only required columns; do not allow direct selection of
  `api_keys.hashed_key`
- decide explicitly which tables are a public Data API and revoke authenticated
  writes from all others
- test direct Supabase calls, not only Next.js route behavior

## 13. Security-critical behavior has no automated regression suite

**Severity:** High  
**Status:** Open

No unit, integration, RLS, concurrency, storage-isolation, API, or browser tests
were found. No `.github/workflows` quality gate was found.

This is a material security issue because the application now relies on subtle
properties that are easy to regress:

- effective migration order and PostgreSQL privilege inheritance
- RLS owner checks and `WITH CHECK` behavior
- service-role delete namespace checks
- credit idempotency and row locking
- webhook event ordering
- account-deletion/upload races
- premium cache isolation

Required minimum suite before launch:

- anonymous and cross-user table/RPC denial tests
- direct Data API tests for every table
- two-user storage delete tests
- concurrent one-credit generation tests
- duplicate and out-of-order webhook tests
- account-deletion race tests
- signup-abuse and route-rate-limit tests
- malformed and oversized upload tests
- Playwright authentication and billing smoke tests
- CI gates for typecheck, lint, tests, migration reset, and production build

# P2 — Medium Priority and Hardening

---

## 14. Input validation is inconsistent and mostly handwritten

Many CRUD routes cast `req.json()` directly to TypeScript interfaces. TypeScript
does not validate runtime JSON. Unknown keys, unbounded strings, large arrays,
invalid URLs, invalid UUIDs, and unexpected nested values often reach Supabase.

Examples:

- `app/api/internal/user/route.ts:41-46`
- `app/api/internal/user/projects/route.ts:92-115`
- `app/api/internal/user/experience/route.ts:41-55`
- `app/api/internal/user/education/route.ts:49-63`
- `app/api/internal/user/education/course/route.ts:72-88`

Use a shared schema library and reject unknown fields. Mirror important limits
with SQL constraints because authenticated clients can call Supabase directly.

---

## 15. Course writes do not validate parent education ownership

The course route writes `user_id = auth user` but accepts an arbitrary
`educationID`. The foreign key verifies that the education row exists, not that
it belongs to the same user.

Evidence: `app/api/internal/user/education/course/route.ts:67-88`

This permits cross-tenant foreign-key attachment and existence probing of
education UUIDs. It does not currently disclose the other user's education
data, but it violates tenant integrity.

Add a composite foreign key `(education_id, user_id)` referencing a unique
`education(id, user_id)` pair, and verify ownership in the route.

---

## 16. Temporary and failed AI storage objects are not consistently cleaned up

Headshot input images remain after many failure paths and after successful
non-premium one-shot generations. Project-thumbnail uploads can remain forever
if the client never creates or updates a project. Generated agent objects are
not always validated or deleted when database caching fails.

Use explicit temporary prefixes, `try/finally` cleanup, object-reference rows,
and bucket lifecycle rules. Treat account deletion as a final safety net, not
the normal garbage collector.

---

## 17. Error responses still reveal internal details in several routes

Examples include:

- storage returns `error.message` to clients on status 500:
  `app/api/internal/storage/route.ts:184-187` and `287-290`
- Stripe routes return Supabase and Stripe messages:
  `stripe/checkout/route.ts`, `stripe/portal/route.ts`, and
  `stripe/checkout/confirm/route.ts`
- webhook signature errors are reflected in the response:
  `stripe/webhook/route.ts:160-172`
- premium cache GET routes return raw database errors

Return stable public error codes and generic messages. Send structured details
to private telemetry with request IDs and redaction.

---

## 18. Security headers are incomplete and CSP permits inline scripts

The application has a useful CSP with `object-src 'none'`, `base-uri 'self'`,
and `frame-ancestors 'self'`. It still allows `'unsafe-inline'` scripts and
styles and broadly permits HTTPS images. No repository configuration sets:

- Strict-Transport-Security
- X-Content-Type-Options
- Referrer-Policy
- Permissions-Policy
- Cross-Origin-Opener-Policy where compatible

Move to nonce- or hash-based scripts, remove obsolete origins, narrow image
sources, prefer `frame-ancestors 'none'` unless embedding is intentional, and
add the missing headers. HSTS should be enabled only after HTTPS is guaranteed
for all relevant subdomains.

---

## 19. CSRF defenses are implicit and inconsistent

Most state-changing routes rely on Supabase cookie defaults and browser
SameSite behavior. Only account deletion performs an explicit Origin check.

SameSite cookies materially reduce cross-site POST risk, but sensitive routes
should not rely on an implicit library default forever. Centralize Origin or
CSRF-token validation for cookie-authenticated mutations, particularly API-key,
billing, password, upload, and account routes. Keep webhook routes exempt and
authenticate them with provider signatures.

---

## 20. OAuth redirect construction trusts proxy forwarding headers

The OAuth callback uses `x-forwarded-host` to construct a production redirect:
`app/api/internal/auth/callback/route.ts:38-46`.

This is safe only if the deployment platform strips attacker-supplied values
and writes a trusted header. Prefer an allowlisted configured canonical origin
and allowlisted relative paths. Also `await handleOauthSignup(...)`; it is
currently called without awaiting completion at line 34.

---

## 21. Password policy is weak in committed configuration

The committed Supabase configuration permits six-character passwords with no
complexity requirement (`supabase/config.toml:181-185`). The signup route adds
no stronger server-side rule.

Use at least 10-12 characters, reject known compromised passwords, permit long
passphrases, enable secure password changes, and encourage MFA. Verify the
hosted project rather than assuming local config matches production.

---

## 22. Logging and monitoring are not security-grade

Logging is mostly unstructured `console.error` output. There is no visible
central audit event model or alerting for:

- authentication and recovery events
- API key creation, rotation, and revocation
- account deletion
- storage upload/delete volume
- AI charge/refund anomalies
- agent latency and timeout rate
- Stripe ownership conflicts
- repeated authorization failures

Public API logs are useful, but descriptions rather than immutable key IDs are
the primary visible label, and high-volume logging itself can become a cost
vector. Add structured, redacted telemetry with retention and alert rules.

---

## 23. Dependency and build reproducibility need attention

The lockfile records Next.js 15.5.23 while the installed tree and production
build report Next.js 15.5.22. `eslint-config-next` is 15.4.5. This drift makes
local validation less reproducible and may leave a security patch unapplied in
the installed environment.

The production build completed but emitted Edge-runtime warnings because the
middleware dependency graph reaches a Node API through Supabase packages.

Current vulnerability status could not be certified because the npm advisory
query was unavailable in this environment. Before launch:

- run `npm ci` in a clean CI runner
- run `npm audit --omit=dev` and a second independent dependency scanner
- review all findings rather than applying blind major upgrades
- align Next.js and `eslint-config-next`
- avoid beta CLI dependencies in production build contexts
- generate and retain an SBOM
- enable automated dependency update PRs

---

## 24. Database deployment state is not continuously verified

The repository migrations are substantially safer, but security depends on all
of them being applied to every hosted project in order. No CI evidence proves
that production matches the repository or that old routine overloads and grants
are absent.

Add a deployment verification script that queries:

- applied migration versions
- all table, sequence, schema, and routine ACLs
- all RLS-enabled/forced flags
- all policies and commands
- all `SECURITY DEFINER` functions and `search_path` settings
- all exposed function overloads
- bucket visibility and storage policies

Fail deployment on drift.

# Positive Security Controls Confirmed

The following controls are worth retaining:

- `auth.getUser()` is used rather than trusting a client-supplied user ID
- service-role credentials are confined to server modules
- no committed secret was found by repository scan
- `.env*` files are ignored
- API key secrets are generated with 32 random bytes
- only an HMAC digest is stored; full keys are shown once
- API key expiry is enforced during public lookup
- the public lookup is bound to the key row's `user_id`
- the old three-argument Super Key function is dropped
- anonymous and `PUBLIC` database object privileges are revoked
- sensitive credit RPCs are service-role-only
- credit balances cannot become negative
- credit consumption is transactional and row-locked
- credit mutations have idempotency conflict checks
- Stripe webhook signatures are verified from the raw body
- invoice credit grants are idempotent
- stale failed-payment events cannot override a successful grant for the same
  invoice
- cached premium AI outputs are read through authenticated, tier-gated server
  routes
- account deletion uses a server-managed lock
- service-role storage paths use server-generated UUID names and user namespaces
- normal storage delete routes verify both path ownership and DB references
- no `dangerouslySetInnerHTML`, `eval`, or obvious raw HTML sink was found
- external project links use `noopener noreferrer`
- TypeScript and ESLint pass
- production build completes

# Final Verdict

Nukleio has moved from obvious authorization failures to a more mature security
posture. The database and credit-system fixes are real, not cosmetic. The
application is suitable for private testing with trusted users and closely
monitored spend.

It is not yet safe for unrestricted public launch.

The decisive blockers are economic and cross-system rather than basic RLS:
agent deployments must authenticate Nukleio, account farming must not mint
unlimited free work, and storage must have enforceable quotas and private-object
handling. Once those controls are implemented and backed by automated tests and
deployment verification, the project should be reaudit-ready for a launch
decision.
